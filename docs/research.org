** public scenario scenario format

A scenario directory holds =index.json= (title, steps, =intro.courseData=
background setup script, =backend.imageid=), Markdown step texts, a setup
script and a =verify.sh= per step that passes with exit code 0. Creators publish
by pushing to a GitHub repository linked to their profile. Environments are
kubeadm clusters named =controlplane= and =node01= at fixed IPs
=172.30.1.2= and =172.30.2.2=; scripts run as root on the control plane.

** Gaps when converting a scenario 1:1

- Node names, fixed IPs and =ssh node01= do not exist on kind; the kubeadm
  backend names its workers =worker-1= and =worker-2=.
- Names are hard-coded, so there are no params and every attempt is the same.
- One exit code per step: no goal/guard split, so the per-check failure
  statistics degrade to one check.
- Many =verify.sh= scripts compare YAML structure with =jq= instead of
  behaviour. That contradicts the rule that every valid solution gets full
  credit.
- The solution sits in a =<details>= block of the step text; there are no
  separate hints, explanation, objectives or difficulty.
- No owned resources or cleanup, so reset and scoped cleanup cannot cover them.

** Decision

No live integration with any provider. A later =cka dev scenario-source=
command may turn a permissively licensed scenario into a draft lab:
=setup.sh= as a =script= step, =verify.sh= as one =script= goal check,
=task.md= from the step text without the solution, =solution.sh= from the
solution block, and the source repository, commit and license recorded. The
draft enters the catalog only after an author adds objectives, hints and
behavioural checks and =cka dev verify= passes.

Labs were separated by certification first (=data/curricula/=,
=labs/<cert>/<domain>/=, =--cert=), so authored CKAD content has a place to go.

* Adopted conventions

exam-source/public scenario's shell setup/validation split is reused, but with typed
Pydantic metadata and read-only behavioral checks. Exit codes remain useful for
host scripts; the evaluator adds structured actual-vs-expected details.

The platform uses kind for fast API-level work and a separate Vagrant/libvirt
kubeadm backend for node/control-plane realism. It does not pretend one
backend can model both a shared host kernel and an independent VM kernel.

* Deliberate non-goals

- No remote web service or paid-platform dependency.
- No machine-learning recommendation system; weakness is a transparent
  Laplace-smoothed failure rate, with hint use reducing a pass's credit and
  older results weighted less (21-day half-life).
- No actual exam questions or claim of official scoring.
- No Gateway controller in the first 22-lab catalog: it would add a large
  offline image dependency for one competency. The schema and curriculum map
  leave the objective ready for a future verified lab.
